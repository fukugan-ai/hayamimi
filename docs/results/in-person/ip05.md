## run が見た物

`played.events.jsonl` の `final` は 4 件で、`lang` は manifest の行の順（ja、en、ja、en）に並んだ。

| id | `lang` | `t1_s` | 受け取った時刻（`t_us`） |
|---|---|---|---|
| `file-1` | ja | 7.316 | 18216506 |
| `file-2` | en | 12.8 | 22254312 |
| `file-3` | ja | 21.792 | 31137627 |
| `file-4` | en | 28.096 | 37531284 |

4 行の窓の `t_start_us`（`played.jsonl`）は 10346249、16598756、22998771、32190514 だった。
`hayamimi-eval` の割り当ては、`final` の `t1_s` を窓の `t_start_us` と比べて決める（`latency.rs` の `placement_us`）。
`file-1` の `t1_s` 7.316 s は最初の窓の始まり 10.35 s より前なので、どの窓にも入らず、`finals_total` が 3 になった。
`file-2` から `file-4` は 1 つ前の窓へ入り、error の `["en"]`、`["ja"]`、`["en"]`、`[]` になった。

窓の `t_start_us` の時計は、`stream` が起動した時刻から数える。
`stream` は `eval.ingest.ready` を待ってから音声を送る。この run では起動が 14:41:10、`ready` が 14:41:19 で、9 s の差があった。
`t1_s` の時計は、`hayamimi` が音声を受け取り始めた所から数える。
`t1_s` に 9.03 s（窓 1 の `t_start_us` 10.346 s から、行 7 の `start_sample` 21040 の 1.315 s を引いた値）を足して窓に当てると、4 件の `final` は窓 1 から窓 4 へ 1 件ずつ入る。この足し算は、この記録の手の計算であり、test の関数の出力ではない。
2 つの時計の差が、割り当てが 1 つずれた理由と読める。直したかどうかは、この席では確かめていない。code は変えていない。
